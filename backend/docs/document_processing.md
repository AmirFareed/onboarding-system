# Phase 6: Document Processing & Text Extraction

Document processing is the phase that turns uploaded files into **raw text**.
Every technically valid document is routed to the right extraction path, its
text is merged in page order, and the result plus its extraction metrics is
stored for the field-extraction and rule-engine phases.

- Module: `backend/app/document_processing/`
- Endpoints:
  - `POST /api/v1/applications/{application_id}/process-documents`
  - `GET  /api/v1/applications/{application_id}/ocr-results`
- Results table: `ocr_results` (Phase 2, reused and extended with metric columns)

## 1. Why document routing is required

Not every PDF is equal, and neither is every document. The pipeline must decide
**how** a document's text will be obtained because the cheapest correct path
varies enormously:

- A PDF generated by a computer (an e-contract, an exported statement) embeds a
  text layer that can be read directly and perfectly.
- A scanned PDF is just a container of page images — the "text" only exists as
  pixels and must be recognized with OCR.
- A standalone image (JPEG/PNG scan) is the same case without the PDF wrapper.

Routing on the document's actual content (`validators.classify_document_source`)
avoids two failure modes: OCR-ing a digital PDF (slow, error-prone, and
worse quality than the embedded text) and treating a scan as a text PDF
(which yields nothing). Routing is what lets the pipeline spend OCR compute
only where it is necessary.

## 2. Why digital PDFs bypass OCR

OCR converts pixels to text with imperfect accuracy; a digital PDF's embedded
text layer is **already exact**. Recognizing it would:

- Be slower (model inference per page) with zero accuracy benefit.
- Introduce recognition errors into text that was never ambiguous.
- Waste the compute budget that the timeout handling protects.

So digital PDFs are read natively with PyMuPDF (`page.get_text()`), which is
fast, lossless and gives no confidence score (there is no recognition to score —
`overall_confidence` is `NULL`). A PDF is only routed as *digital* when its
probed selectable text averages at least `MIN_DIGITAL_TEXT_CHARS_PER_PAGE = 40`
characters per page; otherwise the pages are treated as scans and OCR'd. A flat
total-character threshold used to let scanner-app exports (e.g. CamScanner,
which stamps a short watermark as real text on every page) slip through as
"digital" with nothing but watermark noise extracted.

## 3. How PyMuPDF is used

PyMuPDF (`fitz`) is the module's PDF layer, used in three places:

- **Source classification** (`validators.classify_document_source`): opens the
  PDF, checks for encryption, reads every page's embedded text via
  `page.get_text()` and decides digital vs. scanned. The probed text and page
  count are reused by the extractor so the file is never read twice.
- **Scanned PDF rendering** (`utils.render_pdf_pages`): rasterizes every page at
  200 DPI with `Matrix(dpi/72, dpi/72)` into numpy images that feed the OpenCV
  preprocessing and OCR stages.
- **Digital extraction** (`processors.DigitalPdfExtractor`): packages the probed
  text, engine id `pymupdf`, method `PYMUFPDF_TEXT_EXTRACTION`, page count and
  character count into the extraction result.

A PDF that cannot be opened is a `CorruptedDocument`; an encrypted PDF is never
processed.

## 4. How OpenCV preprocessing works

Images and rendered PDF pages are not fed to OCR raw — they pass through
`utils.preprocess_image`, which runs a four-stage pipeline:

1. **Grayscale** (`COLOR_BGR2GRAY`) — OCR needs a single channel.
2. **Deskew** (`deskew_image`) — estimates the dominant rotation with a Hough
   transform over the Canny edges (reusing `estimate_rotation_angle` from
   technical validation) and rotates the image upright, filling the border
   white. Skewed scans otherwise degrade detection/recognition accuracy.
3. **Denoise** (`bilateralFilter`) — suppresses sensor and compression noise
   while preserving text edges, which a plain blur would destroy.
4. **Contrast enhancement** (`CLAHE`) — local histogram equalization makes faint
   or unevenly lit text distinct without amplifying noise globally.
5. **Adaptive thresholding** (`adaptiveThreshold`, Gaussian + `THRESH_BINARY`) —
   binarizes the page so uneven illumination cannot wash out the text.

The result is a binary image with upright, denoised, high-contrast text — the
best input for PaddleOCR.

## 5. How PaddleOCR is integrated

PaddleOCR is behind the `OCREngine` protocol (`processors.py`):

- `PaddleOCREngine` wraps the PaddleOCR predictor. The `PaddleOCR` instance is a
  process-wide singleton (models download and load once, not per request) with
  document orientation classification, unwarping and textline orientation
  **disabled** — the module already deskews and the pipeline only needs plain
  text recognition.
- `PaddleOCREngine.extract` runs `predict` over a preprocessed image, parses the
  result's `rec_texts` / `rec_scores` arrays, joins the lines with newlines and
  reports the mean `rec_scores` value as `overall_confidence` (the 2.x nested
  list shape is parsed defensively too). Two adapters sit between the pipeline
  and the predictor: the binary grayscale image is expanded to three channels
  (`_to_predict_image`) because the Paddle predictor rejects 2D input, and MKLDNN
  is disabled because consecutive predictions over differently-sized images
  crash the predictor with a native `std::exception` (PaddlePaddle/PaddleOCR
  #17787).
- The service builds engines through the module-level `ocr_engine_factory`
  (dependency injection seam). Tests substitute a fake engine; production uses
  `PaddleOCREngine`. OCR is only invoked for `SCANNED_PDF` and `IMAGE` sources,
  and only when a document actually needs it.
- Engine/import failures surface as `OCRProcessingFailed`; a document whose OCR
  yields nothing is an `EmptyExtraction`.

## 6. Why OCR results are stored

`process` persists one `OCRResult` row per processed document (via
`OCRRepository.upsert`) with the raw text and the full metric set: OCR engine,
processing method, processing time, overall confidence, page count, character
count and completion timestamp. Storing means:

- **Downstream phases can read the text** — field extraction needs the raw text,
  and the rule engine needs confidence/page metrics, without re-OCR-ing files.
- **The pipeline is resumable and auditable** — the `GET /ocr-results` endpoint
  returns stored history; re-processing a document updates its single row
  (`document_id` is unique) rather than duplicating it.
- **No new table is needed** — the Phase 2 `ocr_results` table was extended with
  four additive nullable columns (`processing_method`, `page_count`,
  `character_count`, `processed_at`) via one migration; existing rows and other
  writers are untouched.

## 7. How this module integrates with the rest of the pipeline

- **Technical Validation (Phase 5)**: the processing gate. Every document must
  have a stored `PASS` technical report before it is processed; failing or
  unvalidated documents are skipped (and an application with documents but no
  reports at all is refused with `TechnicalValidationRequired`). Routing itself
  reuses Phase 5's blur/rotation estimator for deskewing.
- **Field Extraction (later phase)**: consumes the stored `raw_ocr_text`. The
  text this phase produces is exactly what field extraction parses; it never
  runs before a document's text exists.
- **Business Rule Engine (later phase)**: reads `overall_confidence`,
  `processing_method` and `page_count` from `ocr_results` so rules can weigh
  low-confidence or OCR-derived data differently from native digital text.
- **Validation Reports**: the stored OCR metrics and document processing status
  (`COMPLETED`/`FAILED`) become part of the per-document record that reports and
  the review workflow summarize.

## Out of scope

Field extraction, data normalization, value validation, signature/stamp
detection and business rules are **not** implemented here; the phase ends after
raw text and extraction metrics are stored.
